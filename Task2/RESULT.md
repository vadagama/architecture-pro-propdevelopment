# Проверочный лист по безопасности бизнес-систем PropDevelopment

## Обоснование выбора разделов

### Выбранные разделы и причины включения

**I. Управление доступом** — включён как приоритетный раздел. Обоснование:
- В описании прямо указано, что клиенты видят в личном кабинете данные другого клиента (чужое ФИО) — это симптом нарушения контроля доступа.
- Множественные точки регистрации клиентов без координации создают риск дублирования и путаницы учётных записей.
- API партнёров (управляющих компаний) позволяют партнёру одной УК видеть/изменять данные клиентов другой УК — отсутствие разграничения доступа между организациями.
- Единственный специалист по ИБ при нарушенной коммуникации между командами — повышенный риск неконтролируемого доступа.
- В архитектуре используются два раздельных Active Directory (для финансовых и для прикладных систем) и Keycloak (auth-service-1) — необходимо проверить согласованность политик.
- Критические риски (утечка учётных данных и токенов) и  (несанкционированный доступ к «Умному дому») напрямую связаны с управлением доступом.

**II. Безопасность данных** — включён как приоритетный раздел. Обоснование:
- Нарушен контроль данных — одна из двух глобальных проблем компании. Внутренние потоки данных контролируются не системно, ограничения обусловлены только бизнес-процессами, а не техническими мерами.
- Есть критические риски, и все они связаны с утечкой или искажением данных (ПДн клиентов, собственников, данные сделок, токены).
- Передача сырых данных через CDC из 5+ баз данных (crm-db, client-mart-db, client-mart-estate-db, tenant-core-db, crm-tenant-db) в единое хранилище Greenplum без системного контроля.
- Компания планирует развивать BI/ML/AI-продукты на базе данных — без Data Governance это невозможно.
- Интеграция с госорганами (СМЭВ через SOAP) и Платёжной системой требует особых мер защиты данных.
- Регуляторные риски по ФЗ-152 «О персональных данных» — недавняя утечка у конкурента усиливает актуальность.

**III. Защита инфраструктуры** — включён. Обоснование:
- Гибридная инфраструктура (собственный ЦОД + облачные ресурсы) создаёт расширенную поверхность атаки.
- Доступ внешних пользователей через firewall указан в описании, но нет данных о сегментации сети.
- Множественные интеграции: REST API между сервисами, Kafka для публикации каталога, SOAP для госорганов, WebSocket для мобильного приложения — каждый канал требует защиты.
- Критические системы (client-mart-app с данными сделок, accountant-service-1 с финансовыми данными) должны быть изолированы.

**IV. Управление инцидентами** — включён. Обоснование:
- Единственный специалист по ИБ, которому не передают все решения и изменения — отсутствие системного процесса реагирования.
- Недавняя утечка у конкурента — руководство обеспокоено и хочет предотвратить подобные инциденты.
- Подтверждённый инцидент с подменой профилей клиентов — непонятно, как он был обнаружен и отработан.
- Компания готовится к комплексному аудиту безопасности — без процесса управления инцидентами аудит не может быть полноценным.

**V. Специфические аспекты** — включён частично. Обоснование:
- V.1 (Общие вопросы): Мобильное приложение для собственников (iOS, Android) — требует MDM и контроля устройств. Облачные ресурсы используются для тестирования — нужны политики резервного копирования.
- V.2 (Физическая безопасность): Собственный ЦОД — необходим контроль физического доступа и инвентаризация оборудования.
