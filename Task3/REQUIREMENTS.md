# Требования к внешним интеграциям: сервисы «Умный дом»

## 1. Требования к безопасности

### 1.1. Защита биометрических данных
- Биометрические данные (изображения лиц) относятся к специальной категории персональных данных согласно ФЗ-152. Обработка допускается только при наличии письменного согласия субъекта данных.
- Биометрические шаблоны (векторные представления лиц) должны храниться и обрабатываться исключительно на стороне платформы партнёра. PropDevelopment не хранит и не передаёт сырые биометрические данные — только идентификаторы привязки (reference ID).
- Партнёр обязан обеспечить шифрование биометрических шаблонов at-rest (AES-256) и in-transit (TLS 1.2+).
- При удалении пользователя из системы PropDevelopment партнёр обязан удалить все связанные биометрические данные в течение 24 часов.

### 1.2. Защита данных автомобильных номеров
- Государственные регистрационные номера автомобилей относятся к персональным данным в связке с данными о собственнике.
- Списки разрешённых номеров передаются партнёру в привязке к идентификатору объекта недвижимости, без раскрытия персональных данных собственника.
- Журнал событий распознавания номеров хранится не более 30 дней, после чего подлежит автоматическому удалению.

### 1.3. Сетевая безопасность
- Весь трафик между PropDevelopment и платформой партнёра должен проходить через выделенный API-шлюз (smart-home-gateway), который обеспечивает:
  - терминацию TLS (минимум TLS 1.2, рекомендуется TLS 1.3);
  - IP-whitelisting — только разрешённые IP-адреса партнёра;
  - rate limiting — ограничение частоты запросов для защиты от DoS;
  - журналирование всех входящих и исходящих запросов.
- Прямое взаимодействие между внутренними сервисами PropDevelopment и платформой партнёра запрещено — все вызовы маршрутизируются через smart-home-gateway.
- Webhook-уведомления от партнёра должны быть подписаны (HMAC-SHA256) для подтверждения подлинности источника.

### 1.4. Изоляция данных (multi-tenancy)
- Платформа партнёра обязана обеспечить строгую изоляцию данных между жилыми комплексами PropDevelopment:
  - Собственник ЖК не может получить доступ к устройствам и данным другого ЖК .
  - API-запросы содержат обязательный идентификатор жилого комплекса (complex_id), который верифицируется на стороне smart-home-gateway перед отправкой партнёру.
- Данные одной управляющей компании не должны быть доступны другой управляющей компании через API партнёра (аналогично текущей проблеме с API поставщиков ЖКХ — эта проблема не должна повториться).

### 1.5. Журналирование и аудит
- Все действия по управлению доступом (добавление/удаление лиц, номеров, открытие дверей/шлагбаумов) должны фиксироваться в журнале аудита с указанием:
  - кто инициировал действие (user_id);
  - когда (timestamp, UTC);
  - что было сделано (action_type);
  - над каким объектом (device_id, complex_id).
- Журнал аудита хранится не менее 1 года и доступен для проверки специалистом по ИБ.

### 1.6. Управление уязвимостями
- Партнёр обязан предоставлять отчёты о пентестах не реже 1 раза в год.
- При обнаружении уязвимостей, затрагивающих данные PropDevelopment, партнёр уведомляет в течение 24 часов.
- SLA на устранение критических уязвимостей — не более 72 часов.

## 2. Протоколы аутентификации и авторизации

### 2.1. Аутентификация собственников (mobile app → PropDevelopment)
- Используется существующий сервис аутентификации auth-service-1 (Keycloak).
- Протокол: **OAuth 2.0 / OpenID Connect (OIDC)**.
- Мобильное приложение получает access token через Authorization Code Flow.
- Access token содержит claims: user_id, complex_id, apartment_id, roles.
- Время жизни access token — не более 15 минут; refresh token — не более 24 часов.

### 2.2. Межсервисная аутентификация (smart-home-gateway → платформа партнёра)
- Протокол: **OAuth 2.0 Client Credentials Grant**.
- smart-home-gateway аутентифицируется на сервере авторизации партнёра с помощью client_id и client_secret.
- Секреты хранятся в защищённом хранилище (Vault) и ротируются не реже 1 раза в 90 дней.
- Каждый запрос к API партнёра содержит Bearer token в заголовке Authorization.

### 2.3. Аутентификация webhook-вызовов (платформа партнёра → smart-home-gateway)
- Партнёр подписывает каждый webhook-запрос с помощью HMAC-SHA256.
- Подпись передаётся в заголовке X-Signature-256.
- smart-home-gateway верифицирует подпись перед обработкой события.
- Дополнительно: проверка timestamp запроса (replay protection, окно — не более 5 минут).

### 2.4. Авторизация действий собственника
- Авторизация на уровне PropDevelopment (перед отправкой запроса партнёру):
  - Собственник может управлять только устройствами, привязанными к его жилому комплексу и квартире.
  - Проверка прав выполняется в smart-home-app на основании данных из CRM собственников (complex_id, apartment_id).
- Модель авторизации — **RBAC** (Role-Based Access Control):
  - owner — полный доступ: управление домофоном, шлагбаумом, редактирование списков доступа (лица, номера).
  - resident — ограниченный доступ: открытие двери по звонку, просмотр видео, без редактирования списков доступа.
- Изменение списков разрешённых лиц и номеров требует подтверждения через push-уведомление (second factor).

### 2.5. Аутентификация IoT-устройств
- Домофон и шлагбаум аутентифицируются на платформе партнёра с помощью **mTLS** (mutual TLS) — каждое устройство имеет уникальный клиентский сертификат.
- Сертификаты устройств управляются партнёром. PropDevelopment не участвует в аутентификации устройств напрямую.

## 3. Организация взаимодействия между системами

### 3.1. Паттерны взаимодействия

| Сценарий                            | Направление                                                             | Протокол                    | Паттерн                 |
| ----------------------------------- | ----------------------------------------------------------------------- | --------------------------- | ----------------------- |
| Открытие двери по звонку домофона   | Мобильное приложение → smart-home-gateway → Партнёр                     | REST/HTTPS                  | Синхронный запрос-ответ |
| Открытие шлагбаума                  | Мобильное приложение → smart-home-gateway → Партнёр                     | REST/HTTPS                  | Синхронный запрос-ответ |
| Уведомление о звонке в домофон      | Партнёр → smart-home-gateway → smart-home-events → Мобильное приложение | Webhook + Kafka + WebSocket | Асинхронный (push)      |
| Результат распознавания лица        | Партнёр → smart-home-gateway → smart-home-events                        | Webhook + Kafka             | Асинхронный (event)     |
| Результат распознавания номера      | Партнёр → smart-home-gateway → smart-home-events                        | Webhook + Kafka             | Асинхронный (event)     |
| Получение видеопотока домофона      | Мобильное приложение → Партнёр (через relay)                            | WebRTC / HLS                | Потоковый (stream)      |
| Управление списком доступа (лица)   | smart-home-app → smart-home-gateway → Партнёр                           | REST/HTTPS                  | Синхронный запрос-ответ |
| Управление списком доступа (номера) | smart-home-app → smart-home-gateway → Партнёр                           | REST/HTTPS                  | Синхронный запрос-ответ |

### 3.2. Контракт API партнёра (ключевые требования)

- Версионирование API: обязательная поддержка версий (/api/v1/...). Партнёр обязан поддерживать предыдущую версию не менее 6 месяцев после выпуска новой.
- Формат данных: JSON (Content-Type: application/json).
- Идемпотентность: все мутирующие операции (открытие двери, изменение списка доступа) должны быть идемпотентными (заголовок Idempotency-Key).
- Пагинация: для списковых операций обязательна курсорная пагинация.
- Коды ошибок: стандартизированный формат ошибок с полями error_code, message, details.                       |

### 3.3. Обработка сбоев

- При недоступности платформы партнёра smart-home-gateway применяет паттерн **Circuit Breaker**
- Для критических команд (открытие двери/шлагбаума) — retry с exponential backoff (максимум 3 попытки, 1с → 2с → 4с).
- При длительном сбое партнёра (>5 минут) — push-уведомление собственнику о недоступности сервиса.
